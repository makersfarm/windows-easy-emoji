# Windows 앱개발 E2E 테스트 30일간 무료로 자동화하기

> 목적: 이 문서는 바로 공개할 블로그 초안이 아니라, 나중에 블로그 글을 쓸 때 디테일을 놓치지 않기 위한 히스토리/재료 정리다.  
> 기준일: 2026-05-11  
> 프로젝트: `makersfarm/windows-easy-emoji`

## 1. 배경: 내가 개발하고 있던 것

개발하던 앱은 Windows 기본 이모지 패널(`Win + .`)을 한국어 검색 친화적으로 대체하는 작은 Windows 네이티브 앱이다.

핵심 아이디어는 다음과 같다.

- Windows 트레이에 상주한다.
- 사용자가 기존 습관대로 `Win + .`을 누르면 기본 Windows 이모지 패널 대신 자체 검색 오버레이를 띄운다.
- 한국어, 영어, 초성, 별칭, shortcode 검색을 지원한다.
- 검색 결과에서 `Enter`를 누르면 이전에 포커스되어 있던 앱에 바로 이모지를 붙여넣는다.
- 설정에 따라 자동 붙여넣기를 끄고 clipboard copy-only 모드로 쓸 수 있다.
- `Win + .` 가로채기가 안 되는 환경을 대비해 fallback hotkey도 둔다.

현재 구현 스택은 다음과 같다.

- .NET 8
- WPF
- xUnit
- Windows Forms `NotifyIcon` interop
- Win32 P/Invoke
- `WH_KEYBOARD_LL` low-level keyboard hook
- `RegisterHotKey`
- `Clipboard.SetText`
- `SendInput(Ctrl + V)`

제품 관점에서 중요한 동작은 단순한 함수 호출이 아니라 Windows 데스크톱 전체 상태와 엮여 있다.

> [이미지 콜아웃] 앱이 실제로 대체하려는 기본 Windows 이모지 패널 화면. 가능하면 `Win + .`을 눌렀을 때 뜨는 기본 패널과, 한국어 검색이 기대만큼 잘 되지 않는 예시를 같이 캡처하면 배경 설명에 좋다.

- 어떤 window가 foreground인지
- `Win + .`이 OS 기본 패널로 가지 않고 앱에 의해 suppress되는지
- overlay가 실제 foreground를 가져오는지
- `Enter`가 overlay 안에서 선택 동작으로 처리되는지
- 붙여넣기가 이전 target window로 들어가는지
- clipboard가 의도한 대로 보존/복원되는지
- tray app, global hook, hotkey가 로그인된 사용자 desktop session에서 제대로 동작하는지

이런 성격 때문에 일반 unit test만으로는 핵심 제품 가치를 검증하기 어렵다.

## 2. 문제 인식: 왜 E2E 테스트가 필요했나

처음에는 core search, settings, paste coordinator 등을 unit test로 검증했다. 그러나 실제 문제가 터지는 지점은 대부분 OS 통합 경계였다.

특히 중요했던 문제는 다음 두 가지였다.

1. `Win + .`을 앱이 실제로 가로채는가
2. overlay에서 `Enter`를 눌렀을 때 이전에 포커스되어 있던 window에 바로 붙여넣기가 되는가

두 번째가 가장 중요했다. 앱 입장에서는 `Clipboard.SetText` 후 `SendInput(Ctrl + V)`만 하면 될 것처럼 보이지만, 실제로는 아래 요소가 모두 맞아야 한다.

- target window handle을 overlay를 띄우기 전에 기억해야 한다.
- overlay가 뜨면서 target handle을 덮어쓰면 안 된다.
- paste 전에 target window를 다시 foreground로 가져와야 한다.
- `SetForegroundWindow`는 Windows foreground lock 정책 때문에 단순 호출만으로 실패하거나 무시될 수 있다.
- `SendInput` P/Invoke 구조체 크기가 x64에서 정확해야 한다.
- clipboard를 설정한 뒤 target app이 읽을 시간을 확보해야 한다.
- test target process가 실제 텍스트 입력을 받을 수 있어야 한다.

실제로 E2E 하네스를 만들면서 아래 문제를 잡았다.

> [이미지 콜아웃] Windows Easy Emoji overlay가 target 입력창 위에 떠 있는 화면. 검색어 `하트`와 첫 번째 결과 `❤️`가 보이면 "제품이 실제로 하는 일"을 한 장으로 보여줄 수 있다.

- overlay는 보이지만 실제 foreground가 아니어서 `Enter` 처리가 불안정했다.
- `SetForegroundWindow` 단순 호출만으로는 target activation이 안정적이지 않았다.
- `SendInput` 호출이 Win32 error 87로 실패했다. 원인은 x64에서 `INPUT` union 구조체에 mouse input layout이 빠져 크기가 틀렸던 점이었다.
- app 설정 파일이 사용자 `%APPDATA%`에 고정되면 E2E 테스트 간 상태가 섞인다.
- app 내부 이벤트를 관찰할 diagnostic log가 없으면 실패 원인 파악이 어렵다.

그래서 E2E 테스트에는 단순 assertion 외에도 다음 로그를 남기게 했다.

- `driver.log`: test driver가 보낸 입력, foreground window 상태, target text 확인
- `app.log`: app startup, keyboard hook, overlay activation, paste lifecycle, clipboard lifecycle
- `target.log`: test target window의 ready/text-changed 이벤트
- `settings.json`: 테스트별 격리 settings
- `ui-e2e.trx`: xUnit test result

## 3. 상황: 왜 로컬에서 돌리면 안 됐나

처음에는 로컬 PC에서 E2E를 돌렸다. 하지만 이 방식은 장기적으로 부적합했다.

문제는 다음과 같다.

> [이미지 콜아웃] 로컬 개발 PC에서 여러 창이 떠 있는 상태로 UI E2E를 돌리면 foreground/clipboard가 테스트에 의해 바뀔 수 있다는 상황 이미지. 실제 코드보다 "사용자 작업 환경을 건드린다"는 느낌이 드는 화면이 좋다.

- 내 실제 작업 환경의 foreground window, clipboard, keyboard input을 테스트가 건드린다.
- `Win + .`, `Ctrl+V`, clipboard mutation 같은 동작이 다른 프로세스에 영향을 줄 수 있다.
- 테스트 중 마우스/키보드 조작을 사람이 건드리면 결과가 흔들린다.
- GUI E2E를 안정화하려면 화면 잠금, 절전, RDP 세션, 권한, monitor/session 상태까지 관리해야 한다.
- Codex/agent가 로컬에서 계속 테스트하면 사용자 작업 흐름을 방해한다.
- 로컬 리소스도 부족하고, 장기적으로 CI에서 자동화하기 어렵다.

즉 이 테스트는 일반 headless browser E2E처럼 격리된 container에서 돌릴 수 있는 성격이 아니다.

필요한 것은 다음 조건을 만족하는 전용 Windows UI E2E 환경이었다.

- 실제 Windows desktop session
- 로그인된 interactive user
- 잠기지 않은 화면
- foreground window 제어 가능
- clipboard 접근 가능
- `SendInput` 가능
- tray app 실행 가능
- low-level keyboard hook 가능
- GitHub Actions에서 원격으로 job을 줄 수 있음

## 5. 핵심 해결 방법: GitHub Actions + self-hosted Windows runner

### 5.1 구조

최종 구조는 다음과 같다.

> [이미지 콜아웃] GitHub Actions와 Cloud PC runner 구조를 간단한 다이어그램으로 만든 이미지. GitHub Actions -> self-hosted runner -> Cloud PC desktop -> WPF app/test target 흐름이 보이면 좋다.

```text
GitHub Actions
  workflow_dispatch: UI E2E
  runs-on: [self-hosted, windows, ui-e2e]
        |
        v
Windows 365 Cloud PC
  logged-in interactive desktop session
  C:\dev\actions-runner\run.cmd
        |
        v
repo checkout
dotnet restore
dotnet build Debug
dotnet test WindowsEasyEmoji.E2ETests
        |
        v
WPF tray app + E2E target app + SendInput
```

GitHub self-hosted runner 자체는 무료로 사용할 수 있다. 다만 실행되는 머신, 즉 Windows 365 Cloud PC 비용은 별도다. artifact/cache/storage 사용량도 GitHub 과금 정책에 영향을 받을 수 있다.

GitHub 공식 문서:

- Self-hosted runners reference: https://docs.github.com/en/actions/reference/runners/self-hosted-runners
- Using self-hosted runners in a workflow: https://docs.github.com/en/actions/how-tos/managing-self-hosted-runners/using-self-hosted-runners-in-a-workflow
- Using labels with self-hosted runners: https://docs.github.com/en/actions/hosting-your-own-runners/managing-self-hosted-runners/using-labels-with-self-hosted-runners

### 5.2 runner는 service로 설치하면 안 됨

UI E2E에서는 이 부분이 핵심이다.

runner를 Windows service로 설치하면 session 0에서 실행될 수 있다. session 0에서는 다음 동작이 깨진다.

- foreground window 제어
- tray UI
- clipboard 접근
- `SendInput`
- desktop focus
- overlay activation

따라서 runner는 반드시 로그인된 Cloud PC desktop session 안에서 `run.cmd`로 실행해야 한다.

정상 상태:

> [이미지 콜아웃] Cloud PC 안의 PowerShell에서 `.\run.cmd`가 실행 중이고 `Connected to GitHub`, `Listening for Jobs`가 보이는 화면. runner가 "켜져 있어야 하는 프로세스"라는 점을 직관적으로 보여준다.

```powershell
cd C:\dev\actions-runner
.\run.cmd
```

PowerShell 창이 닫히지 않고 다음과 같은 로그가 떠 있어야 한다.

```text
Connected to GitHub
Listening for Jobs
```

runner 창이 프롬프트로 돌아오면 runner가 실행 중이 아니다.

### 5.4 workflow

`UI E2E` workflow는 수동 실행만 허용했다.

> [이미지 콜아웃] GitHub Actions의 `UI E2E` workflow 화면에서 `Run workflow` 버튼과 branch 선택 dropdown이 보이는 캡처. 나중에 따라 하는 독자가 어느 화면에서 실행하는지 알 수 있다.

```yaml
name: UI E2E

on:
  workflow_dispatch:

jobs:
  windows-desktop:
    name: Windows desktop UI E2E
    runs-on: [self-hosted, windows, ui-e2e]
    timeout-minutes: 30

    defaults:
      run:
        shell: powershell

    env:
      WINDOWS_EASY_EMOJI_RUN_UI_E2E: "1"
      WINDOWS_EASY_EMOJI_E2E_ARTIFACT_DIR: ${{ github.workspace }}\artifacts\ui-e2e

    steps:
      - uses: actions/checkout@v6.0.2
      - run: .\scripts\assert-ui-e2e-session.ps1
      - uses: actions/setup-dotnet@v5.2.0
        with:
          dotnet-version: 8.0.x
      - run: dotnet restore WindowsEasyEmoji.sln
      - run: dotnet build WindowsEasyEmoji.sln --configuration Debug --no-restore
      - run: >
          dotnet test tests\WindowsEasyEmoji.E2ETests\WindowsEasyEmoji.E2ETests.csproj
          --configuration Debug
          --no-build
          --logger "trx;LogFileName=ui-e2e.trx"
          --results-directory artifacts\TestResults
      - if: always()
        uses: actions/upload-artifact@v4
        with:
          name: ui-e2e-${{ github.run_id }}-${{ github.run_attempt }}
          if-no-files-found: warn
          path: |
            artifacts/ui-e2e
            artifacts/TestResults
```

중요한 부분:

- `runs-on: [self-hosted, windows, ui-e2e]`
- `WINDOWS_EASY_EMOJI_RUN_UI_E2E=1`
- `shell: powershell`
- artifact upload

처음에는 `shell: pwsh`를 썼다가 Cloud PC에 PowerShell 7이 없어 실패했다.

> [이미지 콜아웃] 실패한 Actions run의 annotation 또는 log에서 `pwsh: command not found`가 보이는 화면. "일반 Windows에는 pwsh가 없을 수 있다"는 실수 사례로 쓰기 좋다.

```text
pwsh: command not found
```

그래서 Windows 기본 PowerShell로 고정했다.

```yaml
defaults:
  run:
    shell: powershell
```

### 5.5 session preflight

`scripts/assert-ui-e2e-session.ps1`는 runner가 UI E2E에 적합한 session에서 실행 중인지 검증한다.

> [이미지 콜아웃] Actions 로그의 `Verify interactive desktop session` step. `sessionId=2`, `userInteractive=True`, `administrator=True`, `UI E2E session looks usable`가 보이는 캡처를 넣으면 "headless가 아니라 실제 desktop session에서 돌고 있다"는 증거가 된다.

확인한 값:

- 현재 user
- process session id
- `[Environment]::UserInteractive`
- administrator 여부
- `query user` 출력

성공 로그 예시:

```text
UI E2E session check
user=AzureAD\YoonMinwook
sessionId=2
userInteractive=True
administrator=True
query user:
>yoonminwook ... Active ...
UI E2E session looks usable.
```

주의할 점:

`query user`는 diagnostic 용도인데, Windows PowerShell에서 native command의 `$LASTEXITCODE`가 남아 step 전체가 실패할 수 있었다. 실제 managed checks는 통과했는데도 GitHub Actions가 exit code 1로 step을 실패 처리했다.

해결:

```powershell
$global:LASTEXITCODE = 0
```

성공 경로 끝에서 native exit code를 명시적으로 초기화했다.

## 6. Windows 365 Cloud PC 설정 순서

### 6.1 Cloud PC 준비

1. Windows 365 trial을 준비한다.
2. https://windows.cloud.microsoft/#/devices 또는 Windows App으로 Cloud PC에 접속한다.
3. 화면 잠금/절전이 테스트 중 끼어들지 않게 한다.
4. PowerShell을 관리자 권한으로 실행한다.
5. 권한을 확인한다.

> [이미지 콜아웃] Cloud PC에서 관리자 권한 PowerShell을 연 화면. 창 제목에 `Administrator: Windows PowerShell`이 보이면 좋다.

```powershell
whoami /groups
```

초기에는 다음 상태가 나왔다.

```text
Mandatory Label\Medium Mandatory Level
BUILTIN\Administrators  Group used for deny only
```

이 상태는 elevated shell이 아니다. UI E2E 자체는 반드시 admin일 필요는 없지만, runner setup/power config 등 초기 설정은 elevated shell이 안전하다. 정상적인 관리자 PowerShell이면 `High Mandatory Level`이고 Administrators가 enabled 상태여야 한다.

### 6.2 repo checkout

Cloud PC에서:

```powershell
git clone https://github.com/makersfarm/windows-easy-emoji.git C:\dev\windows-easy-emoji
cd C:\dev\windows-easy-emoji
git checkout main
git pull origin main
```

처음에는 PR branch를 checkout했지만, PR이 main에 merge된 뒤에는 `main`만 쓰면 된다.

> [이미지 콜아웃] GitHub organization settings의 runner group 설정 화면. `Repository access`에서 `All repositories` 또는 selected repo가 보이는 화면이 좋다.

### 6.4 runner 설치

처음에는 사용자가 cmd에서 `.ps1`을 직접 실행해 Notepad가 열렸다. 원인은 cmd에서 PowerShell script를 직접 호출했기 때문이다.

cmd에서 실행하려면:

```cmd
powershell -NoProfile -ExecutionPolicy Bypass -File .\scripts\setup-cloudpc-ui-e2e-runner.ps1 -RunnerRoot "C:\dev\actions-runner" -RunnerToken "<token>"
```

PowerShell에서 실행하려면:

## 7. .NET E2E 테스트 프레임워크 구조

### 7.1 테스트 프로젝트

E2E는 별도 xUnit 프로젝트로 뒀다.

```text
tests/WindowsEasyEmoji.E2ETests
```

실제 입력을 받을 target app도 별도 프로젝트로 만들었다.

```text
tests/WindowsEasyEmoji.E2ETarget
```

target app은 WinForms `TextBox`를 가진 단순 창이다. 목적은 실제 paste target을 통제 가능하게 만드는 것이다.

> [이미지 콜아웃] Cloud PC에서 E2E target window가 떠 있고, WPF overlay가 그 위에 뜬 화면. target window title이 `WindowsEasyEmoji E2E Target ...`로 보이고 overlay title이 `Windows Easy Emoji`로 보이면 좋다.

target app 역할:

- window title을 고유하게 설정
- ready file에 window handle 기록
- TextBox text 변경 시 text file에 기록
- target.log에 ready/text-changed 기록

### 7.2 E2E session

`E2ESession`이 한 테스트마다 다음을 만든다.

> [이미지 콜아웃] GitHub Actions artifact zip을 열었을 때 `app.log`, `driver.log`, `target.log`, `target.txt`, `ui-e2e.trx`가 보이는 파일 목록. 테스트 결과를 화면이 아니라 파일로 증명한다는 메시지를 강화한다.

```text
artifacts/ui-e2e/<guid>/
  app.log
  driver.log
  target.log
  target.ready
  target.txt
  settings.json
```

시작 순서:

1. 기존 `WindowsEasyEmoji.App` process kill
2. test별 temp/artifact directory 생성
3. test별 settings.json 생성
4. WPF app 실행
5. app log에서 `keyboard-hook.start` 대기
6. target WinForms app 실행
7. target ready file 대기
8. target window foreground focus

종료 시:

- app process kill
- target process kill
- logs를 xUnit output에도 기록

### 7.3 UI 입력 방식

키 입력은 `SendInput` P/Invoke를 사용한다.

현재 테스트 helper:

- `SendWinPeriod()`
- `SendFallbackHotkey()`
- `SendEnter()`
- `SendEscape()`
- `TypeSearchText(string)`
- `ClickWindowCenter(IntPtr handle)`

Unicode 검색어 입력은 `KEYEVENTF_UNICODE`를 쓴다. 그래서 `ㅋㅋ`, `ㄸㅂ` 같은 한국어/초성 검색도 실제 UI 입력으로 검증한다.

### 7.4 Clipboard 검증

clipboard는 STA thread에서 접근해야 한다.

테스트 helper는 별도 STA thread를 만들어:

- `SetClipboardText`
- `GetClipboardText`

를 실행한다.

copy-only mode나 restore clipboard mode는 target text만 봐서는 부족하므로 clipboard assertion이 필요했다.

### 7.5 E2E skip gate

일반 CI에서 UI E2E가 실행되면 hosted runner/headless-ish 환경에서 깨질 수 있다.

따라서 custom Fact attribute를 만들었다.

```csharp
[UiE2EFact]
```

환경 변수가 없으면 skip한다.

```text
WINDOWS_EASY_EMOJI_RUN_UI_E2E=1
```

일반 `dotnet test WindowsEasyEmoji.sln`에서는 E2E가 skip된다.  
`UI E2E` workflow에서는 env를 켜서 실제로 실행한다.

## 9. 실제로 겪은 실패와 해결

### 9.1 로컬에서 테스트하려다 방향이 틀어짐

처음에는 로컬에서 E2E를 실행했다. 하지만 목표는 Cloud PC에서 완전 자동 디버그 가능한 전용 E2E 환경을 만드는 것이었다.

교훈:

- Windows UI E2E는 "테스트 코드가 있다"보다 "어디서 실행되는가"가 더 중요하다.
- local interactive machine과 dedicated interactive VM은 완전히 다르게 취급해야 한다.

### 9.2 runner token을 채팅에 붙여넣음

runner token을 채팅에 붙여넣었다.

runner token은 짧게 만료되고 1회성 성격이 강하지만, 노출되면 폐기하고 새로 발급하는 것이 원칙이다.

문서에는 다음을 명시했다.

```text
token을 채팅이나 로그에 붙여넣었다면 폐기하고 새 token을 만든다.
```

### 9.3 `.ps1` 실행 시 Notepad가 열림

cmd에서 `.ps1`을 직접 실행하면 Windows file association 때문에 Notepad가 열릴 수 있다.

해결:

```cmd
powershell -NoProfile -ExecutionPolicy Bypass -File .\scripts\setup-cloudpc-ui-e2e-runner.ps1 ...
```

또는 애초에 PowerShell에서 실행한다.

### 9.4 `Test-Path run.cmd`와 `.runner`가 false

`start-cloudpc-ui-e2e-runner.ps1`를 실행했는데 아무 로그 없이 프롬프트로 돌아왔다. 확인해보니:

```powershell
Test-Path C:\dev\actions-runner\run.cmd
Test-Path C:\dev\actions-runner\.runner
```

둘 다 false였다.

즉 runner setup이 아직 안 된 상태였다. `start`가 아니라 `setup`부터 다시 해야 했다.

### 9.5 org runner가 repo에 안 보임

org-level runner로 등록하면 repo settings의 self-hosted runner 화면에서 안 보이거나, repo가 사용할 수 없을 수 있다.

확인할 것:

- org runner group
- repository access
- repo 허용 여부
- runner labels

### 9.6 runner가 Offline

GitHub 화면에서 runner가 offline이면 Cloud PC의 `run.cmd`가 실행 중이 아니다.

해결:

```powershell
cd C:\dev\actions-runner
.\run.cmd
```

### 9.7 `pwsh: command not found`

Cloud PC에 PowerShell 7이 없었다. workflow에서 `shell: pwsh`를 쓰면 실패했다.

해결:

```yaml
defaults:
  run:
    shell: powershell
```

### 9.8 session check는 성공했는데 step exit code 1

로그:

> [이미지 콜아웃] session check 로그가 성공 메시지를 찍었는데도 마지막에 `Process completed with exit code 1`이 보이는 Actions log 화면. native command exit code가 왜 위험한지 보여주는 사례다.

```text
sessionId=2
userInteractive=True
administrator=True
UI E2E session looks usable.
Process completed with exit code 1.
```

원인:

- `query user`는 diagnostic 용도였는데 `$LASTEXITCODE`가 1로 남았다.
- GitHub Actions PowerShell wrapper가 이를 step failure로 처리했다.

해결:

```powershell
$global:LASTEXITCODE = 0
```

### 9.9 artifact warning

테스트가 실제 실행 전 단계에서 죽으면 artifact 경로가 아직 없다.

로그:

```text
No files were found with the provided path: artifacts/ui-e2e artifacts/TestResults.
```

이 warning 자체가 원인이 아니다. 앞 단계 실패 때문에 artifact가 없는 것이다.

### 9.10 Node.js 20 warning

GitHub Actions에서 `actions/upload-artifact@v4`가 Node.js 20 deprecation warning을 냈다.

> [이미지 콜아웃] Actions summary의 warnings 영역. Node.js 20 warning과 artifact warning이 보이는 화면을 넣으면, 어떤 warning은 원인이 아니고 노이즈일 수 있다는 설명에 좋다.

이 warning은 당시 실패 원인이 아니었다. 이후 GitHub Actions runtime 변화에 맞춰 action version 또는 env를 조정하면 된다.

### 9.11 branch UI E2E run이 checkout 이전에서 멈춤

PR #4 branch에서 UI E2E를 수동 실행했을 때 runner가 job을 잡았지만 steps가 비어 있고 checkout 이전에서 멈췄다.

상태:

```text
status=in_progress
steps=[]
runner_name=CPC-infos-DTMBO-ui-e2e
```

`gh run cancel`과 force-cancel 요청을 넣었지만 즉시 처리되지 않았다.

추정:

- self-hosted runner process가 job을 잡은 상태에서 응답하지 못하는 상태
- Cloud PC runner 창에서 `Ctrl+C`로 끊고 `run.cmd`를 다시 실행해야 함

이건 테스트 코드 failure가 아니라 runner lifecycle 문제로 분리해서 봐야 한다.

## 10. 개발 패턴

### 10.1 E2E에서 실제 OS boundary를 테스트하되, 관찰 가능성을 먼저 만든다

Windows UI E2E는 실패하면 원인이 많다.

- hook 실패
- window focus 실패
- overlay activation 실패
- keyboard event 실패
- target focus 실패
- clipboard 실패
- paste 실패
- test target 문제
- runner session 문제

따라서 diagnostic log를 먼저 넣어야 한다.

이번에 넣은 로그 이벤트:

- `app.startup begin/complete`
- `keyboard-hook.start`
- `keyboard-hook.win-period`
- `hotkey.register`
- `tray.show-overlay`
- `foreground.get`
- `tray.activate-overlay`
- `main-window.focus-search-box`
- `main-window.paste-result`
- `paste.start`
- `foreground.activate`
- `clipboard.paste`
- `clipboard.restore`
- `paste.complete`

### 10.2 test별 settings path override

실제 앱은 `%APPDATA%\WindowsEasyEmoji\settings.json`를 사용한다.

E2E에서는 test isolation을 위해 환경 변수로 override한다.

```text
WINDOWS_EASY_EMOJI_SETTINGS_PATH
```

이렇게 하면 테스트별로 settings를 주입할 수 있다.

- auto paste on/off
- clipboard restore on/off
- fallback hotkey on/off
- replace Win+. on/off

### 10.3 일반 CI와 UI E2E를 분리한다

일반 CI:

- hosted Windows runner
- unit/platform tests
- E2E는 skip

UI E2E:

- self-hosted Windows runner
- interactive desktop
- E2E env on
- artifact upload

이 분리가 중요하다. 모든 PR마다 UI E2E를 강제로 돌리면 runner availability에 PR이 막힐 수 있다.

### 10.4 target app을 직접 만든다

Notepad 같은 외부 앱으로 paste 테스트를 할 수도 있지만 불안정하다.

직접 만든 E2E target app이 더 낫다.

- window title 고유화
- handle 기록 가능
- text 변경 파일 기록 가능
- 로그 기록 가능
- UI 구조 단순

### 10.5 UI E2E는 "사람이 보는 화면"보다 "파일/로그로 증명"한다

VM 화면에서 메모장이나 창이 잠깐 뜨는 것은 사람이 보면 헷갈린다.

테스트 결과는 아래로 판단한다.

- GitHub Actions status
- xUnit result
- artifact logs
- target text file
- app diagnostic log
