# .NET과 WPF 초심자 설명 및 프로젝트 선택 이유

## 목적

이 문서는 `.NET`과 `WPF`를 처음 접하는 사람이 Windows Easy Emoji 프로젝트의 기술 선택을 이해할 수 있도록 정리한 문서다.

핵심은 다음 한 문장이다.

`.NET`은 앱을 실행하고 코드를 작성하게 해주는 기반이고, `WPF`는 그 위에서 Windows 화면을 만드는 UI 프레임워크다.

즉 `.NET`과 `WPF`는 서로 경쟁하는 선택지가 아니다. 이 프로젝트는 `.NET`으로 만들고, UI는 `WPF`로 만든다.

## 비유로 이해하기

집을 짓는다고 생각하면 다음처럼 볼 수 있다.

- `.NET`: 전기, 수도, 철근, 공구, 작업 규칙 같은 기본 인프라.
- `C#`: 사람이 실제로 쓰는 작업 언어.
- `WPF`: 창문, 문, 벽, 조명, 가구 배치를 만드는 인테리어/건축 방식.
- Windows Easy Emoji: 실제로 지으려는 작은 작업실.

따라서 ".NET을 쓸까, WPF를 쓸까?"는 정확한 질문이 아니다. 더 정확히는 ".NET으로 앱을 만들 때 화면은 WPF로 만들까, WinUI 3 같은 다른 UI 프레임워크로 만들까?"가 맞다.

## .NET이란

`.NET`은 Microsoft가 만든 개발 플랫폼이다. C# 같은 언어로 코드를 작성하고, 그 코드를 빌드하고, 실행하고, 라이브러리를 가져다 쓸 수 있게 해준다.

이 프로젝트에서 `.NET`이 담당하는 것은 다음과 같다.

- C# 코드 실행.
- 프로젝트 빌드.
- 파일 읽기/쓰기.
- JSON 처리.
- 테스트 실행.
- NuGet 패키지 사용.
- Windows API를 호출하기 위한 기반 제공.
- 앱을 exe/publish 형태로 배포하는 기반 제공.

`.NET`만으로도 콘솔 프로그램, 웹 서버, 테스트 도구, 데이터 처리 도구를 만들 수 있다. 하지만 사용자가 보는 Windows 창, 버튼, 검색창, 설정창을 만들려면 UI 프레임워크가 필요하다.

## WPF란

`WPF`는 Windows Presentation Foundation의 약자다. `.NET` 위에서 Windows 데스크톱 앱의 화면을 만들기 위한 UI 프레임워크다.

WPF가 담당하는 것은 다음과 같다.

- 앱 창 만들기.
- 검색창, 버튼, 리스트, 그리드 같은 UI 요소 만들기.
- XAML로 화면 구조 선언하기.
- C# code-behind로 동작 연결하기.
- 스타일, 색상, 레이아웃 적용하기.
- 설정창 같은 보조 창 만들기.
- 오버레이 창을 화면 위에 띄우기.

우리 앱에서 사용자가 실제로 보는 검색 오버레이, 결과 그리드, 설정 창은 WPF로 만든다.

## .NET과 WPF의 관계

`.NET`은 큰 기반이고, `WPF`는 그 기반 위에 올라가는 Windows UI 도구다.

관계는 이렇게 볼 수 있다.

| 구분 | .NET | WPF |
| --- | --- | --- |
| 역할 | 앱을 만들고 실행하는 기반 | Windows 화면을 만드는 UI 프레임워크 |
| 범위 | 웹, 콘솔, 서버, 데스크톱, 테스트 등 넓음 | Windows 데스크톱 UI에 집중 |
| 사용 언어 | 주로 C# | 주로 XAML + C# |
| 우리 앱에서 하는 일 | 검색 로직, 데이터 처리, 설정 저장, 테스트, 빌드 | 검색창, 결과 그리드, 설정창, 오버레이 표시 |
| 대체 관계인가 | 아님 | .NET 위에서 선택하는 UI 방식 |

## Windows Easy Emoji에서 실제로 나뉘는 구조

현재 프로젝트는 대략 다음처럼 나뉜다.

- `WindowsEasyEmoji.Core`: 이모지 데이터, 검색, 랭킹, 사용자 상태 같은 핵심 로직.
- `WindowsEasyEmoji.Platform`: 클립보드, 키보드 훅, foreground window, Windows API 연결.
- `WindowsEasyEmoji.App`: WPF 앱 UI, 트레이 앱, 검색 오버레이, 설정 창.
- `tests`: 검색 품질 테스트, 플랫폼 테스트, VM 기반 UI E2E 테스트.

여기서 `Core`와 `Platform`은 최대한 UI와 분리한다. 검색 품질이나 붙여넣기 정책은 WPF에 묶이면 안 된다.

반대로 `App`은 사용자가 보는 화면이므로 WPF를 사용한다.

## 왜 이 프로젝트에서 WPF가 좋은가

### 1. 우리가 만드는 앱은 작은 Windows 유틸리티다

Windows Easy Emoji는 거대한 문서 편집기나 브라우저가 아니다. 시스템 트레이에 떠 있다가 단축키를 누르면 작은 검색창을 띄우고, 고른 이모지를 원래 입력창에 붙여넣는 도구다.

이런 앱에는 빠르게 띄울 수 있는 작은 창, 설정창, 트레이 메뉴, 전역 단축키, 클립보드 처리가 중요하다. WPF는 이런 Windows 데스크톱 유틸리티를 만들기에 충분히 적합하다.

### 2. 전역 단축키와 Windows API를 많이 쓴다

이 앱은 일반 UI 앱보다 Windows 내부 기능과 많이 붙는다.

- `Win + .` 대체를 위한 keyboard hook.
- fallback hotkey.
- 현재 활성 창 기억.
- 원래 입력창으로 focus 복원.
- 클립보드에 이모지 복사.
- `Ctrl+V` 전송.
- 시스템 트레이 상주.

WPF는 오래된 데스크톱 프레임워크라 이런 Win32 API와 섞어 쓰는 자료와 사례가 많다. MVP 단계에서는 이 안정성이 중요하다.

### 3. 빠르게 MVP를 만들 수 있다

우리 제품의 핵심 경쟁력은 "한국어로 이모지를 잘 찾고 바로 붙여넣는 것"이다.

초기에는 UI 프레임워크 자체를 깊게 연구하는 것보다 검색 데이터, 검색 랭킹, 붙여넣기 안정성, 설정 저장을 빠르게 완성해야 한다. WPF는 검색창, 그리드, 설정창, 트레이 메뉴를 빠르게 구현할 수 있다.

### 4. 배포가 단순하다

오픈소스 MVP는 사용자가 쉽게 실행해볼 수 있어야 한다. WPF는 `.NET publish`로 exe와 필요한 파일을 묶어 배포하기 쉽다.

나중에 Microsoft Store 배포를 검토할 수 있지만, 지금은 먼저 "다운받아서 실행 가능한 앱"이 더 중요하다.

### 5. UI를 나중에 바꿀 수 있게 구조를 나눌 수 있다

지금 WPF를 쓴다고 해서 영원히 WPF에 갇히는 것은 아니다.

검색 엔진, 데이터 스키마, 사용자 상태, 붙여넣기 로직을 `Core`와 `Platform`에 잘 분리해두면, 나중에 UI만 WinUI 3나 다른 프레임워크로 바꾸는 선택지도 남는다.

그래서 현재 전략은 "핵심 로직은 UI와 분리하고, MVP UI는 WPF로 빠르게 만든다"다.

## WPF를 선택하면 생기는 단점

WPF가 무조건 최고라는 뜻은 아니다.

단점도 있다.

- 기본 디자인이 최신 Windows 11 앱처럼 보이지 않을 수 있다.
- 컬러 이모지 폰트 렌더링이 항상 기대대로 되지 않는다.
- 최신 WinUI 컨트롤이나 Windows App SDK 기능을 바로 쓰기 어렵다.
- 소비자용 앱으로 polish를 극대화하려면 나중에 UI 개선이 필요하다.

그래서 우리 앱은 WPF `TextBlock`만 믿지 않고, 검색 결과의 이모지 표시는 Twemoji 같은 컬러 이미지 리소스를 사용한다. 붙여넣기는 이미지가 아니라 표준 유니코드 문자열을 그대로 사용한다.

## 최종 정리

이 프로젝트는 `.NET`과 `WPF` 중 하나를 고른 것이 아니다.

정확한 선택은 다음과 같다.

1. 앱 개발 기반은 `.NET`을 사용한다.
2. 언어는 C#을 사용한다.
3. Windows 화면은 WPF로 만든다.
4. 검색/데이터/붙여넣기 핵심 로직은 WPF에 묶이지 않게 분리한다.

WPF를 선택한 이유는 이 앱이 Windows 시스템 유틸리티이기 때문이다. 전역 단축키, 트레이 상주, 작은 오버레이, 클립보드, 원래 입력창으로 붙여넣기 같은 기능을 빠르게 안정적으로 구현하는 데 WPF가 현실적으로 좋다.

나중에 앱이 커지고 Windows 11 네이티브 디자인이 핵심 경쟁력이 되면 WinUI 3 전환을 다시 검토할 수 있다. 하지만 지금 단계의 성공 조건은 프레임워크 최신성이 아니라 검색 품질과 붙여넣기 경험이다.
